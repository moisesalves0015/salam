# Sala de Missões — análise do projeto e prompt completo para concluir o Firebase

Repositório analisado: [`moisesalves0015/salam`](https://github.com/moisesalves0015/salam). O README identifica o produto como **Sala de Missões**, um ecossistema pedagógico gamificado para estudantes do 4º e 5º ano.

## Diagnóstico do estado atual

O projeto **não começa do zero**. Já existe um backend Express/TypeScript com Firebase Admin, coleções e tipos do Firestore, regras, validações Zod, rotas para algumas entidades, serviços de negócio, script de seed e testes unitários. A configuração do servidor prevê Firestore, Auth e Storage. O `.env.example` lista variáveis para Admin SDK e Firebase Web SDK, mas isso não equivale a uma integração Web funcionando: o `package.json` não declara o pacote `firebase`, `src/main.tsx` apenas monta o React e não há provedor/contexto de autenticação inicializando o SDK no cliente.

O README é explícito: Firebase Authentication está marcado como “futuro”; o frontend ainda não está plenamente integrado a `src/services/api.ts`; há pendências de loading/error handling, testes com Emulator e deploy. Portanto, a instalação existente é uma **fundação parcial**, não um sistema conectado e pronto para produção.

O bloqueio principal está no fluxo de identidade. `LoginScreen.tsx` permite entrar como professor ou coordenação sem verificar credenciais; no perfil de aluno, qualquer PIN funciona e também existe um botão de entrada direta. `App.tsx` inicializa dados a partir de `INITIAL_STUDENTS`, fixa o papel como professor, mantém alunos/cards/conquistas/métricas em estado local e não restaura uma sessão autenticada. O papel não deve ser definido por seleção na interface.

O middleware `server/middleware/auth.ts` ainda é permissivo em desenvolvimento e aceita `X-Mock-Role`; na verificação do token, usa dados do próprio token para montar papel/escopo e assume aluno como papel padrão. O README sugere que essa autenticação ainda não é obrigatória. Isso não é apropriado como regra de produção. A identidade precisa vir de token Firebase válido e o papel/escopo deve ser obtido de um perfil confiável no Firestore ou de custom claims administradas pelo backend, nunca de um valor escolhido pelo cliente.

A API cobre leitura e algumas ações para estudantes, missões, intervenções, cards, conquistas, recompensas e administração de seeds/métricas. Não existe cobertura CRUD completa para contas/convites, escolas, turmas, catálogo de trilhas, missões, habilidades, cards, conquistas, recompensas, ajustes/ledger de moedas ou estados dos resgates. Várias telas — inclusive dashboards, trilhas, relatórios, reconhecimento, notificações, diagnósticos, álbum de cards e loja — recebem objetos de estado ou valores fixos e não carregam dados do backend.

Os pontos de gamificação estão parcialmente modelados (`currentXp`, `coins`, missões, tentativas, transações de moedas, conquistas e cards), mas não são integrados com consistência em todo o frontend. `App.tsx` concede XP e altera habilidade/card/conquista somente em memória ao finalizar algumas missões; `LessonRunner` retorna XP ao app e não persiste a atividade no serviço de API. `LojaMoedasView.tsx` lista produtos codificados em uma constante, usa um saldo padrão de 320 moedas se o dado não existir e apenas registra resgates em estado local. Há endpoint de resgate, mas ele aceita `studentId` do corpo e faz leitura de saldo antes da transação, o que precisa ser protegido contra impersonação e concorrência.

Também há um risco de integridade em `server/services/missionService.ts`: a conclusão concede XP fora da transação que marca a missão concluída, não aplica de fato uma exigência de progresso mínimo antes de concluir e não oferece chave de idempotência. Repetições, falhas parciais ou requisições concorrentes podem resultar em inconsistências ou duplicidade de recompensas. Ajustes de XP/moedas e resgates precisam virar operações auditáveis e atômicas.

As regras `firestore.rules` negam escritas diretas em boa parte dos dados de estudante e ledger, o que é uma boa intenção, mas permitem leitura ampla de alguns catálogos e não aplicam de modo uniforme o escopo por escola/turma. Como Admin SDK ignora Security Rules, a autorização mais importante tem de estar implementada nas rotas/serviços do servidor. Regras de Firestore e Storage também precisam ser testadas no Emulator.

### Telas e áreas que a integração deve cobrir

O mapeamento inclui `LandingPage` e `LoginScreen`; dashboards do aluno, professor e coordenação; `AlunosView` e prontuário (`StudentProfileModal`); trilhas, missões, jogador de missão, `LessonRunner` e versão para impressão; intervenções e seus formulários; diagnóstico e modal de avaliação; relatórios/memória pedagógica; reconhecimento e certificados; cards/álbum, detalhes, conquistas; loja de moedas; painel de sala/TV; notificações; seletor de turma, cabeçalho e preferências do estudante. O conteúdo educacional das atividades — unidades, etapas interativas, exercícios, materiais e temas — está distribuído em tipos e módulos de dados como `src/data/curriculum.ts`, `missionsData.ts`, `mathData.ts` e `initialData.ts`; a implementação deve migrar/seedar os catálogos necessários sem apagar o conteúdo ou alterar a experiência pedagógica.

## Observação de segurança sobre dados reais

O prompt deliberadamente proíbe deploy e migração contra produção sem autorização explícita. Para concluir a implantação, ainda serão necessários acesso/configuração no projeto Firebase `salam-33122` (Auth, Firestore, Rules, índices e eventualmente Storage) e um ambiente de backend com segredos protegidos. Valores de configuração Web podem ser públicos, mas chaves administrativas e tokens não devem ser copiados para o frontend nem enviados em conversas.
